TASKUP: GERENCIADOR DE TAREFAS

Sabrina Rayssa Teixeira
Prof. Ricardo Bicalho
RESUMO

Este artigo apresenta o TaskUp, um gerenciador de tarefas pessoais formado por uma API RESTful e por uma interface que a consome. O objetivo do trabalho é praticar desenvolvimento backend, modelagem de banco de dados e criação de APIs REST em um sistema pequeno. A API foi feita em Node.js com Express e usa o SQLite como banco de dados. Com ela é possível cadastrar, listar, consultar, editar e excluir tarefas. O backend, o banco e a interface web já estão integrados: a interface consome a API para cadastrar usuários, organizar tarefas em categorias, criar checklists de subtarefas, visualizar os detalhes e as subtarefas diretamente na lista, buscar e filtrar tarefas, e listar, criar, editar, concluir e excluir tarefas. A exclusão funciona como uma lixeira, permitindo restaurar a tarefa antes de apagá-la definitivamente. O sistema foi publicado no Render Cloud e está disponível em https://taskup-rffb.onrender.com/.

Palavras-chave: API REST; Node.js; Express; SQLite; gerenciamento de tarefas.

ABSTRACT

This paper presents TaskUp, a personal task manager made of a RESTful API and an interface that uses it. The goal of the work is to practice backend development, database modeling and REST API design in a small system. The API was built with Node.js and Express and uses SQLite as its database. It allows users to create, list, view, edit and delete tasks. The backend, the database and the web interface are now integrated: the interface uses the API to register users, organize tasks into categories, create subtask checklists, view task details and subtasks directly in the list, search and filter tasks, and list, create, edit, complete and delete tasks. Deletion works as a trash bin, so a task can be restored before being permanently removed. The system is deployed on Render Cloud at https://taskup-rffb.onrender.com/.

Keywords: REST API; Node.js; Express; SQLite; task management.

1. INTRODUÇÃO

Um gerenciador de tarefas é uma aplicação fácil de entender e boa para praticar os conceitos da disciplina. O cliente, que é a interface, fica separado do servidor, que guarda os dados e aplica as regras, e os dois conversam por meio de uma API. Assim, a mesma API pode atender uma interface web ou um aplicativo móvel.

O TaskUp foi desenvolvido na unidade curricular Sistemas Distribuídos e Mobile. O objetivo é criar uma aplicação para organizar tarefas e, com ela, aplicar conceitos de backend, banco de dados e APIs RESTful. Como metas, o trabalho definiu implementar as operações básicas sobre as tarefas, integrar o backend a uma interface web e acrescentar recursos de organização, como categorias, subtarefas, prazos, prioridades, filtros e uma lixeira para exclusões reversíveis.

2. FUNDAMENTAÇÃO TEÓRICA E TECNOLOGIAS

2.1. API RESTful

REST é um estilo de arquitetura apresentado por Fielding (2000). Nele, cada coisa que a aplicação manipula é um recurso com um endereço (URL), e as operações usam os métodos do HTTP: GET para consultar, POST para criar, PUT para alterar e DELETE para excluir. A resposta traz um código de status, como 200 (sucesso), 201 (criado), 204 (sem conteúdo), 400 (requisição inválida), 404 (não encontrado) e 409 (conflito). No TaskUp, os recursos principais são usuários, categorias, tarefas e subtarefas, acessados por rotas como /usuarios, /categoria e /tarefas.

2.2. Node.js, Express e SQLite

Foram usados o Node.js, que executa JavaScript no servidor (NODE.JS, [s.d.]), e o Express, um framework que simplifica a criação de rotas (EXPRESS, [s.d.]). O banco de dados é o SQLite, que guarda tudo em um único arquivo e não exige instalar um servidor de banco (SQLITE, [s.d.]). Ele é acessado pelo módulo node:sqlite, disponível a partir do Node.js 22.5. Por isso, as únicas dependências do projeto são o Express e o CORS, este último para liberar o acesso à API a partir de outra origem, como o frontend. O projeto exige Node.js 22.5 ou superior.

3. MODELAGEM E IMPLEMENTAÇÃO

3.1. Funcionalidades

As funcionalidades do TaskUp estão na Tabela 1 e são atendidas pelos endpoints da Tabela 2. O sistema foi pensado para ser simples de usar: cada tarefa pertence a um usuário, pode ter uma categoria, um prazo, uma prioridade e um checklist de subtarefas. A categoria é opcional; quando uma categoria é excluída, as tarefas continuam existindo, mas ficam sem categoria. A busca ignora diferenças de maiúsculas, minúsculas e acentos, e os filtros de status, categoria e busca podem ser combinados. No celular, a navegação principal passa para uma barra inferior, facilitando o uso em telas pequenas.

Além disso, ao clicar em um cartão na lista, a interface expande a descrição, a prioridade, o prazo e as subtarefas da tarefa. Nesse painel, o usuário pode marcar ou desmarcar uma subtarefa e acompanhar o progresso do checklist sem abrir outra janela. O botão “Subtarefas” continua disponível para adicionar ou remover itens.

3.2. Modelo de dados

O banco possui quatro tabelas relacionadas. usuarios armazena nome, telefone e data de criação, com chave primária composta. categorias pertence a um usuário e armazena o nome da categoria. tarefas armazena título, descrição opcional, prazo opcional, prioridade, status e data de criação, além de referenciar o usuário por nome e telefone e, opcionalmente, uma categoria. subtarefas armazena o título, o indicador de concluída e a data de criação de cada item do checklist, referenciando a tarefa. A coluna excluida_em implementa a lixeira: quando está vazia, a tarefa aparece na listagem normal; quando recebe uma data, a tarefa passa a aparecer apenas na lixeira. Quando uma categoria é excluída, as tarefas ligadas a ela ficam sem categoria. Quando uma tarefa é apagada definitivamente, suas subtarefas são apagadas em cascata; enquanto a tarefa está na lixeira, as subtarefas são preservadas para a restauração.

A coluna categoria_id pode ser NULL; ao excluir a categoria, a tarefa permanece sem categoria.

O arquivo db.js cria as tabelas e aplica pequenas migrações; o server.js apenas registra os routers. Cada domínio tem sua própria pasta em src, com as consultas SQL (sql.js) separadas das rotas (routes.js). A Tabela 2 resume os endpoints.

O servidor valida o título obrigatório, o status (pendente ou concluida), a prioridade (baixa, media ou alta) e o formato do prazo (AAAA-MM-DD). A categoria é opcional, mas quando informada precisa pertencer ao mesmo usuário da tarefa. O título da subtarefa é obrigatório e a subtarefa precisa pertencer à tarefa informada na rota. Tarefas que estão na lixeira não aceitam alterações nas subtarefas: é preciso restaurá-las antes. A rota de exclusão definitiva só aceita tarefas que já estão na lixeira.

3.4. Interface web

A interface foi feita com HTML, CSS e JavaScript puro, sem framework. O arquivo config.js define o endereço da API; script.js concentra o estado da aplicação, as chamadas à API e a renderização das telas; index.html organiza as views e os modais; style.css cuida do layout e da responsividade. Há três views principais: Minhas tarefas, Concluídas e Lixeira. Os modais permitem criar e editar tarefas, gerenciar categorias e adicionar ou remover subtarefas. O login é feito com nome e telefone, e o usuário fica salvo no navegador para as próximas visitas. Ao trocar de view, a página volta ao topo para mostrar o resumo geral. Na publicação, o próprio backend entrega os arquivos do frontend, de modo que a mesma URL atende à interface e à API.

4. RESULTADOS PARCIAIS

4.1. Teste do backend e da interface

O backend e a interface foram executados localmente e testados com requisições HTTP e pelo navegador. O cadastro de usuário retornou 201 e um cadastro repetido retornou 409. O cadastro de categoria retornou 201, uma categoria repetida retornou 409 e a edição retornou 200. A criação de tarefa retornou 201 com status pendente, prioridade, prazo e categoria; uma prioridade inválida, um prazo fora do formato e uma categoria de outro usuário retornaram 400. O cadastro de subtarefa retornou 201, a conclusão retornou 200 e a listagem de tarefas passou a mostrar o progresso do checklist. Criar uma subtarefa sem título retornou 400, assim como tentar alterar subtarefas de uma tarefa na lixeira. A conclusão da tarefa retornou 200 e atualizou o status. A exclusão retornou 204, a tarefa saiu da listagem normal e passou a aparecer em /tarefas/lixeira. A restauração retornou 200 e a tarefa voltou para a listagem com suas subtarefas. A exclusão definitiva retornou 204 somente para tarefas na lixeira e apagou as subtarefas em cascata. Uma consulta a uma tarefa apagada retornou 404.

Na interface, foram testados login, gerenciamento de categorias, associação e filtro por categoria, checklist de subtarefas com progresso, busca por título sem diferenciar maiúsculas ou acentos, filtro por status, combinação de filtros, busca na lixeira, criação de categoria pelo formulário de tarefa, navegação pelo menu inferior em tela pequena, criação, edição, conclusão, envio para a lixeira, restauração, exclusão definitiva, persistência após sair e entrar, limpeza dos filtros ao sair e saída do usuário. Também foi testado o clique no cartão da tarefa, que expande a descrição, a prioridade, o prazo e o checklist de subtarefas na própria lista; uma subtarefa pode ser concluída nesse painel e o progresso é atualizado sem fechar o cartão. Ao trocar de tela depois de rolar a lista, a página volta ao topo para mostrar o resumo geral. A Tabela 3 resume os principais testes.

Depois dos testes locais, o sistema foi publicado no Render Cloud e a URL pública foi verificada: a página e a API responderam 200.

5. CONSIDERAÇÕES FINAIS

Nesta etapa, a API do TaskUp permite cadastrar e consultar usuários e categorias e executar operações CRUD em tarefas e subtarefas, com lixeira, restauração, organização por categorias e checklists. O banco valida os dados e vincula cada tarefa a um usuário. A interface web já consome a API e permite gerenciar categorias, buscar e filtrar tarefas e acompanhar o progresso das subtarefas. O sistema foi publicado no Render Cloud em https://taskup-rffb.onrender.com/.
